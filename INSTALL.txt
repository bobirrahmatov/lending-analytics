CACHE CONTRACT
PAL-dashboard.html uses in-memory indexes and memoized results. The new shared
credit-data-cache.js follows that model:
- A page-scoped loader coalesces concurrent reads for each logical dataset.
- Fully validated rows are reused during that page's lifetime.
- WeakMap indexes belong to the exact array, so a new release/snapshot array has
  fresh caches. Filter results are bounded to 24 entries per input array.
- Region, owner, product and facility attributes use exact indexed selections.
- Relationship ranking groups rows once instead of rescanning every facility for
  every relationship. Sums reuse results for the same array and measure.
- Dates are validated once per distinct value during a dataset validation pass.
- Empty results and boolean false are valid cached filters.
- Failed requests/validation are evicted and can be retried. No partial dataset is
  committed. Mixed bundle IDs, invalid types, duplicate primary keys, source/date
  mismatches and source control-count mismatches fail validation.
- Every new document load revalidates attachments with Confluence using the
  current session (credentials same-origin, cache no-cache). This permits normal
  HTTP revalidation; it is not a cache-first authorization bypass. A 403 or a
  sign-in HTML response never falls back to retained financial data.
- No financial data is stored in localStorage, sessionStorage or IndexedDB.
  App caches do not persist between native Confluence document navigations.
  A full reload obtains the latest manifest. An open page stays on one published
  snapshot; background polling and automatic mixed-release refresh are not used.

OPTIONAL LARGE-DATA JSON UTILITIES
The default remains the six stable-name Excel inputs. Standalone JSON validation
and partitioning tools are retained for prepared larger releases. They have no
Microsoft Access dependency. A 75,000-row full-field facility fixture was
139,360,471 UTF-8 bytes before transport compression, exceeding one attachment.
Use parts below the attachment limit for such prepared JSON data.

Both forms are supported for each required dataset:
  "portfolio": {"filename":"credit-portfolio-RELEASE.json","rows":3000}
  "portfolio": {"rows":3000,"parts":[
    {"filename":"credit-portfolio-RELEASE-part-0001.json","rows":1500},
    {"filename":"credit-portfolio-RELEASE-part-0002.json","rows":1500}
  ]}
The numbers above only illustrate descriptor syntax. Size determines the real
part boundaries; every actual payload must be strictly below 10,000,000 bytes.
Every part has schema_version=2, the same bundle_id and its rows. Two requests
run concurrently per dataset; combined records are validated before display.
Primary keys must be unique across all parts, not merely within each part.

Optional Python path for an existing unsplit export:
  python tools/partition_release.py SOURCE_EXPORT NEW_UPLOAD_FOLDER
  python tools/validate_release.py NEW_UPLOAD_FOLDER
This writes content-hashed payload names into a new folder and never modifies the
input. It removes its newly created output if validation fails. Upload all
payloads first and credit-manifest.json last. Retain old payloads for rollback.
Do not reuse a release ID. Do not overwrite live data with illustrative examples.

Optional previous and covenant_history envelopes still use single attachments.
Oversized optional snapshots are rejected rather than silently truncated. Large
comparison/history publication needs a separate nested-dataset partition contract;
it is not covered by the current 75,000-current-facility processing result.
The retained-history utility can read current partitioned releases but still
rejects output exceeding its attachment limits. Do not treat that rejection as a
successful history publication.
