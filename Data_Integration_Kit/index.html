Portfolio Overview versus Underwriter Summary

Portfolio Overview answers: How large is the portfolio, where is exposure concentrated, what is approved or expiring, and what monitoring risk needs attention? It consolidates facility balances, covenant and CCM obligations, and dated history. Underwriter Summary answers: Which obligations need action across the six monitoring areas, who owns them, and where are critical items concentrated? Their overlap is intentional; their counting units differ.

The original Overview is Underwriter Summary, retaining the overview route key and existing page ID. It is the high-level monitoring view. Underwriter Workload remains the detailed owner queue and aging view. Both include specialist-owned obligations where supplied; the title does not introduce an owner-role filter. Portfolio Overview remains the separate PAL financial dashboard. The Sources & definitions page is removed; the sources dataset remains required for validation and lineage.

Published files, primary keys and join keys

Direct Excel descriptors use filename, rows and format="xlsx". Keep all six Metadata sheets and the manifest on the same release. For large JSON datasets, the optional Access exporter writes immutable parts below 8 MB. Those manifest entries supply rows and parts [{filename,rows}], or the original single filename/rows form. The browser combines and validates the entire logical dataset before use; primary keys remain unique across parts. validate_release.py validates JSON publication folders, not XLSX files. No Python runtime is required for the Access export. Optional previous and covenant_history JSON envelopes still require each file below 10 MB. Windows Access compilation and export need validation on the actual Windows installation.

Every JSON envelope uses schema_version=2, the same bundle_id as credit-manifest.json, and rows. Every field in schema.json must be present; optional means null is allowed, not that the field may be silently omitted. Keys are text and must preserve leading zeros. Primary keys below are unique within each dataset/snapshot; across an archive retain as_of_date and bundle_id. Never generate a key from worksheet position.

Required core: monitoring, portfolio, history, activity, sources and documents entries in manifest.files. A file with zero rows is permitted where the source is genuinely unavailable (for example documents); disclose missing coverage. This does not make all financial or analytical views complete. Startup loads monitoring and sources even for Portfolio. Related enrichment failures are isolated so the primary page can remain usable.

Optional previous file: schema_version + current bundle_id + rows (equal to datasets.monitoring), datasets.monitoring/portfolio/activity/sources and retained historical/document data if supplied. Its manifest rows counts previous monitoring rows, not all nested rows. Keys repeat between periods by design; evaluate per snapshot. Daily comparisons require the exact preceding weekday and reconciled matching source coverage.

Optional covenant_history: rows of retained monitoring associations, snapshots with as_of_date, complete flag and source controls, and optional portfolio_rows with portfolio_sources. Identity is (as_of_date,item_id); associated balance history is (as_of_date,facility_key). Use build_covenant_history.py with validated releases, not hand-created aggregate comparisons.

Validation and publishing sequence

1. Confirm source owners, raw formats, stable IDs, reporting dates, eligible populations and coverage. Resolve critical rule_version=proposed-1 thresholds with the business owner. Do not treat proposed rules as signed-off policy.

2. For direct Excel, create the six prepared Data/Metadata workbooks, preserve IDs and typed amounts/booleans, assign one new bundle_id to every file and manifest, and reconcile source counts and dates. For sample use, upload the complete excel/runtime/ attachment set with its sample installation. For production, use approved records and production metadata. Upload the data and optional comparisons first, then the matching manifest. Validate all pages with normal native viewer permissions.

Optional Access/JSON preparation: populate the staging workbook, import the three Access modules and use the existing schema/install workflow. On Windows run ImportCreditInputs and BuildCreditRelease into a new release directory. Retain the prior prepared workbook for the optional previous-snapshot argument. Windows Access execution remains a required dry run; this environment has not executed VBA.

The Python command above validates the included JSON sample release only, not Excel workbooks. For real JSON data use validate_release.py YOUR_RELEASE without --allow-demo. Production rejects is_demo=true. The optional Access publisher retains immutable payload names for its partitioned releases; the direct Excel installation uses the fixed filenames described above. In both paths, publish data and optional comparisons first, then manifest last. All attachments and archives must remain strictly below 10,000,000 bytes.
